# Update Center and Windows desktop updater — safe rollout

**Release state:** ACTIVE ALPHA — NOT RELEASED. Local hotel data and admin credentials are not held in GitHub.

## Current packaged Windows path (V7/V8)

For the installed Windows desktop application, follow [current source-only update policy](KAIZEN_V7_ONE_CLICK_CODE_UPDATES.md), not the developer Git-checkout procedure below. PR #179 decoupled approved source-only patches from installer artifacts; PR #180 permits verified trusted local checkpoints for routine source/UI patches, while preserving independent recovery for protected storage changes and native upgrades. The owner UI must reconcile the full status/readiness SHA before offering Apply. An older supervisor may require a one-time guarded bootstrap. No physical acceptance is implied.

## Legacy/source-checkout workflow (not the packaged Windows instructions)

1. **In-app owner-only Update Center:** My Profile → Application updates → **Check for updates**. This performs read-only Git inspection and compares the local HEAD with GitHub's `refs/heads/main`. It shows **installed and remote** abbreviated commit hashes. It never pulls code, migrates a database, installs packages, restarts Node, or writes guest records. The Git remote must be the approved `tchouhanjsm/fortledger`, the branch must be `main`, and the checkout must have no tracked **or untracked** changes. Offline GitHub, an unexpected remote, or a dirty checkout is a clear block, not a guessed update state. A differing SHA does **not** itself prove the update can fast-forward; the offline updater verifies that separately.
2. **Windows one-double-click launcher (after stopping FortLedger):** open the *existing installed Git checkout*, then double-click `Update FortLedger.cmd` (or create a Windows desktop shortcut to it once). It runs `scripts/windows-quick-update.ps1`. It **never kills an active server**, drops a guest transaction or forces a Git reset. It refuses to continue unless an encrypted `.flbk` backup from the last 36 hours is present in the configured independent backup directory and `npm run recovery:encrypted-drill -- <actual file>` verifies an isolated restore. The existing `windows-update.ps1` then refuses a running localhost listener, unexpected repository/branch, untracked or tracked changes and missing legacy data. It creates a separate verified consistent SQLite + admin authentication snapshot, fetches GitHub `main`, fast-forwards (no force), uses the committed dependency lockfile with `npm ci`, and runs all Node tests. **Only after success** does the launcher start a new normal `windows-start.ps1` PowerShell window. Review old data and sign in again.
3. **Mac updates remain manually gated** under `docs/MAC_RELEASE_PREFLIGHT.md`. No change to the current `data/fortledger.sqlite` Mac path, credential file, or backup configuration. Updating an older Git checkout (for example PR #83) still requires a one-time code sync and conflict review before this Update Center becomes visible locally.

## Windows requirements

- Git for Windows, Node 22.x and PowerShell 5.1+, installed checkout on `main` with `origin` pointing to `tchouhanjsm/fortledger`; a **clean tracked and untracked** Git state.
- Existing persistent database at `%LOCALAPPDATA%\FortLedger\data\fortledger.sqlite` and valid owner authentication. The updater will **not** initialize a blank replacement for a legacy database.
- A separately protected encrypted backup directory, optionally supplied with `FORTLEDGER_BACKUP_DIR` in the launcher environment or entered when the shortcut opens. The launcher prompts privately for `FORTLEDGER_BACKUP_PASSPHRASE` if it is not already available; it does not save the secret in a source file. A successful local encrypted recovery drill is required. An independent restore on a replacement device still needs human acceptance; verifying a local artifact is not proof of off-device recoverability.
- Finish all bookings, payments and bill printing, then stop the active FortLedger terminal with **Ctrl+C**; the listener check refuses updates while the app is running. Run the shortcut locally on the device, not on a staff phone or a LAN browser.
- If a check fails, **the process stops** and reports the blocker. Keep the verified backups and original credential file. Do not delete `data`, `*-wal`, `*-shm` files, or run `git reset --hard` / force-pull. A new app version can introduce a data migration, so automatically reverting code is not a safe rollback plan.

## Why no browser-triggered auto-install yet?

The original browser UI is not a privileged Windows service, so it never executes Git, npm or PowerShell itself. The **Windows-only external supervisor** introduced in this phase starts the Node server as a child process; the authenticated owner-only `POST /api/system/updates/install` sends a pinned 40-character CI-approved SHA to that parent via IPC. A protected local owner confirmation and loopback restriction are required. The server rejects new financial POST/PATCH requests, completes existing HTTP requests and **exits cleanly**; only after observing the clean drain and process exit does the parent run the already-tested backup-first Windows script. The script verifies an isolated encrypted restore, makes a consistent separate snapshot, checks the Git origin, requires a fast-forward to the exact approved commit, installs locked dependencies, runs Node tests and restarts via the existing Windows persistent-data environment.

The owner Update Center now calls `GET /api/system/updates/readiness` and **only shows Install** when all preliminary gates pass: Git main is newer, checkout is clean, separate supervisor is active, backup configuration has a recent encrypted artifact on another drive/share, and the **exact main push SHA** has a completed successful GitHub Actions run including Linux, Windows and Chromium jobs. If the network or official CI proof is unavailable, installation stays disabled.

The parent writes only coarse update state, timestamps and commit SHAs to `%LOCALAPPDATA%\\FortLedger\\update-journal.jsonl` (never guest or passphrase data). If a failure occurs **before changing Git HEAD**, it can restart the previous version; if the code has advanced but installation/tests failed, it **leaves the service stopped** for manual reviewed recovery and never performs an unsafe automatic database rollback. No active request is force-killed by the updater; an owner must still ensure staff have finished typing unsaved forms before initiating it.

**Important limits:** This is an early alpha supervised installer, not a signed-release distribution system. It pins a GitHub main commit with passed CI; immutable signed release tags and cryptographic artifact verification are still future hardening. Windows runtime and off-device restore cannot be certified by CI; no real production financial workstation should be auto-upgraded until supervised physical acceptance. Mac remains manual, and PR #83 Mac installations need a one-time protected code sync before seeing any of these controls.

**No silent updates, paid infrastructure, new runtime dependencies, or Git credentials in the web UI.** The owner must still verify the new revision, hotel records, printer and actual restored backup. Do not interpret a clean update as a production-release certificate.

## Explicit runbook for supervised Windows owner updates

1. Start only with `scripts/windows-start.ps1` so a **separate Node parent supervisor** stays alive when the child app restarts. The persistent data directory is still `%LOCALAPPDATA%\\FortLedger\\data` and is never pulled from GitHub.
2. Configure `FORTLEDGER_BACKUP_DIR` on a **different protected drive/share** from the live database and `FORTLEDGER_BACKUP_PASSPHRASE` privately in the supervisor startup environment. Backup passwords are never typed into the web form. A recent file is not proof of restore; the final update runner executes the full encrypted restore drill.
3. Complete reception/cashier work; the owner checks updates in My Profile and reviews the three-job CI link. The explicit confirmation cautions that unsaved client-side forms should be finished before restart.
4. The app returns HTTP **202 Accepted** only after the external parent confirms the IPC request. The front end must not resubmit on uncertainty. The parent waits for the server to finish every in-flight HTTP response; then it validates CI again and invokes the pinned Windows update script with `-ExpectedCommit` and `-SkipRestart`.
5. If successful, reopen `http://127.0.0.1:3000`, sign in, verify the same rooms/guest records, the installed revision and `npm run doctor`. If the parent reported an install/restart problem, **stop** and inspect the journal/backups without deleting WAL files, force-pulling, or guessing an old database version.

A Windows operator can still use **Update FortLedger.cmd** after manually stopping the app. A Mac must still follow `docs/MAC_RELEASE_PREFLIGHT.md`; the supervised browser action is not enabled on Mac, guest phone or private-LAN access.

## Windows onboarding and DPAPI backup persistence (next batch)
- First setup can now be launched with **Install FortLedger.cmd**; routine operation uses **Start FortLedger.cmd**, protected backup setup uses **Configure FortLedger Backups.cmd**, and a read-only health pass uses **Diagnose FortLedger.cmd**. These are ordinary Windows Explorer shortcuts, not an MSI or Windows service.
- Backup configuration is optionally saved at `%LOCALAPPDATA%\\FortLedger\\backup-settings.json` with **Windows CurrentUser DPAPI**. The passphrase is never recorded as plaintext in a repo file. Startup and manual update scripts reload the protected secret; a missing/wrong-user/corrupt setting keeps automatic installation disabled or fails closed.
- Backups must live on a drive/share with a *different Windows path root* than the live data. This conservative static check does not independently prove encryption, physical isolation, remote replication or recovery: those remain operational acceptance items.
- DPAPI protects a same-user secret on disk; Windows malware running as that user can access process memory and environment. Copying the DPAPI settings file does **not** migrate the passphrase to a new user or machine. Store the original passphrase independently, and rehearse off-device recovery.
- A new PC with existing Mac hotel data is not a new ledger: preserve the consistent SQLite backup **and** `admin-auth.json` before setting up a new owner. The AES-GCM `.flbk` SQLite backups currently do not include the credential file. Do not silently import only one of them.
